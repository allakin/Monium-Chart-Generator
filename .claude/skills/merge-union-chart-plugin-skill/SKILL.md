# Мерж отдельного плагина в сводный

Источник правды по процедуре — [MERGE_GUIDE.md](../../../MERGE_GUIDE.md).
Этот скилл задаёт порядок работы и добавляет обязательный шаг тестирования.

## Шаг 0. Прочитать гайды

1. Прочитать `MERGE_GUIDE.md` целиком — там структура сводного `code.js` и
   `ui.html` по блокам, процедура мержа по категориям A/B/C, соглашения об
   именах и раздел «Key Rules».
2. Прочитать `CHART_STYLE_GUIDE.md` (этого прямо требует Step 0 гайда):
   проверить актуальный список типов чартов, общие параметры стиля (палитра,
   сетка, оси, отступы, легенда, события) и то, что все типы из гайда есть в
   сводном плагине.
3. Если в стайлгайде появился тип, которого нет в сводном плагине — сначала
   раздел «Adding a New Chart Type» гайда.

## Шаг 1. Понять, что изменилось

```bash
git status --short
git diff --stat HEAD
git diff HEAD -- "Chart Line" "Chart Bar" "Chart Area" "Chart Pie"
```

Если направление мержа или набор правок неоднозначны — спросить пользователя
через `AskUserQuestion` (что мержим, из какого плагина, целиком или отдельные
правки). Отдельные плагины — источник правды: правки делаются в них, потом
переносятся в сводный.

Разложить изменения по категориям MERGE_GUIDE:

- **A) Общий код** — палитра, `selectDistinctColors`, отслеживание выделения,
  полосы событий, сетка, подписи осей, построители кривых, `prepareContainer`.
- **B) Код конкретного чарта в `code.js`** — функции отрисовки, `generate*`,
  fallback-парсер слоёв.
- **C) `ui.html`** — поля, радиогруппы, логика видимости, `generate()` /
  `regenerate()`.

## Шаг 2. Базовый прогон тестов ДО мержа

Вызвать скилл `plugins-chart-test-skill` (Skill tool,
`skill: plugins-chart-test-skill`) с аргументом — затронутыми типами чартов,
чтобы он не переспрашивал: например `pie`, `pie,bar` или `all` для правок в
общем коде.

Зафиксировать базовую картину: сколько `pass`, сколько `fail`, сколько `todo`.
Без этого потом не отличить «сломал мержем» от «уже было сломано».

## Шаг 3. Смержить

Строго по процедуре гайда (Steps 2–5). Кратко:

- **Категория A** — заменить функцию в SHARED-секции сводного `code.js`,
  проверить, что другие типы не зависели от старого поведения.
- **Категория B** — найти секцию типа (`═══ CHART [TYPE] ═══`), заменить
  функции; при смене сигнатуры поправить вызов в `generate*`; при новых полях
  `chartParams` — дописать их и в fallback-парсер слоёв.
- **Категория C** — панель `#panel-[type]` в `ui.html`, блоки
  `if (currentTab === '[type]')` в `generate()` и
  `if (chartType === '[type]')` в `regenerate()`, обработчики видимости,
  регистрацию радиогрупп. Имена ID и radio `name` — с префиксом типа.

Красные линии из «Key Rules» гайда, которые легко нарушить при копировании из
отдельного плагина:

- **Не понижать `findChartFrame`** до перебора прямых детей: в сводном плагине
  это BFS по всем потомкам с ограничением ~200 узлов.
- **`prepareContainer` всегда удаляет существующий чарт** из целевого фрейма —
  не оборачивать удаление в проверку `replaceMode`; для определения замены
  использовать флаг `replacedChild`, а не координаты.
- **Имена контейнеров стабильны** (`Chart Line` / `Chart Bar` / `Chart Area` /
  `Chart Pie`) — переименование ломает перегенерацию существующих чартов.
- **Формат `pluginData` обратно совместим** — поля добавляются с дефолтами, но
  не переименовываются и не удаляются.
- **Легенда и счётчик серий**: в сводном плагине подписи легенды нормализуются
  **после** финализации количества серий (в режиме Bar Normal `barsCount`
  сбрасывается в 1). Не переносить обратный порядок из отдельного Chart Bar —
  это его известный баг, он описан в `tests/README.md`.
- **Кнопка «Get values from chart»** видна только когда тип найденного чарта
  совпадает с активной вкладкой; вся логика состояния кнопок — в `switchTab()`.

## Шаг 4. Прогон тестов ПОСЛЕ мержа

Снова вызвать `plugins-chart-test-skill`:

- правки категории B или C по одному типу → аргумент с этим типом;
- правки категории A (общий код) → аргумент `all`: общий код влияет на все
  четыре типа, плюс важны проверки
  «all copies of X behave identically» в `tests/helpers-unit.test.js` — именно
  они ловят расхождение копий функций между пятью плагинами.

Сравнить с базовым прогоном из шага 2:

- новых `fail` нет и число `pass` не упало → мерж чистый;
- появились новые `fail` → это регресс мержа, разбирать и починить до того, как
  отдавать результат; не помечать такие тесты `todo`;
- какой-то `todo` внезапно стал проходить → баг попутно исправлен, снять
  маркер `todo` и записать это в отчёт.

Тесты каждого типа прогоняются сразу против отдельного плагина и против
сводного, поэтому расхождение между реализациями видно как падение ровно в
одном варианте — это основной сигнал, что мерж неполный.

## Шаг 5. Документация и отчёт

- Если менялись общие параметры стиля или добавлялся тип чарта — обновить
  `CHART_STYLE_GUIDE.md`.
- Если в `chartParams` появились новые поля — существующие чарты их не имеют.
  Не писать код миграции по слоям (гайд прямо это запрещает), а указать в
  отчёте и сообщении коммита: «перегенерируйте существующие чарты, чтобы
  подхватить <функцию>».
- В отчёте: что перенесено (по категориям), что прогнано, результат
  до/после, что осталось непокрытым автотестами — и напомнить про ручной
  чек-лист `tests/MANUAL_QA.md`, если правка влияет на внешний вид или на окно
  плагина.
- Не коммитить без явной просьбы.
