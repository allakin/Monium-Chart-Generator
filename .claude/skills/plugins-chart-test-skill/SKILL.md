# Тестирование плагинов чартов

Прогон автотестов из `tests/` против настоящего `code.js` каждого плагина
(Node + мок Figma Plugin API). Зависимостей нет, нужен Node ≥ 20.
Устройство харнесса и список известных багов — в [tests/README.md](../../../tests/README.md).

## Шаг 1. Спросить, что тестировать

Если в аргументах вызова уже названы плагины или типы чартов
(`/plugins-chart-test-skill pie`, `... pie,bar`, `... all`, `... изменённые`) —
**вопрос не задавать**, сразу перейти к шагу 2.

Иначе задать вопрос через `AskUserQuestion`:

- **header:** `Что тестировать`
- **question:** `Какие плагины прогнать?`
- **options:**
  1. `Все сразу (рекомендуется)` — 503 теста, ~0.5 с, полная картина
  2. `Отдельные типы чартов` — уточню, какие именно
  3. `Только изменённые` — по `git status` соберу затронутые плагины
  4. `Только матрица размеров` — быстрая проверка на «график не отображается»
     на фреймах от 1200×800 до 20×20

Если выбран вариант 2 — вторым вопросом уточнить типы
(`multiSelect: true`, options: `Pie`, `Line`, `Area`, `Bar`).

Важно объяснить в ответе: **сьюта каждого типа чарта прогоняется сразу против
двух реализаций** — отдельного плагина и соответствующей вкладки сводного
генератора, поэтому отдельно «тестировать сводный плагин» не нужно.

Для варианта 3 определить затронутое так:

```bash
git status --short && git diff --name-only HEAD
```

Пути → типы: `Chart Pie/*` → `pie`, `Chart Line/*` → `line`,
`Chart Area/*` → `area`, `Chart Bar/*` → `bar`.
Изменения в `Monium all charts generator/*` или в общем коде (палитра,
`selectDistinctColors`, сетка, оси, легенда, полосы событий, `prepareContainer`)
→ прогонять **все** типы: общий код влияет на каждый чарт.

## Шаг 2. Запустить

Все тесты:

```bash
npm test
```

Только матрица размеров:

```bash
node --test tests/small-frames.test.js
```

Отдельные типы чартов (подставить нужный тип в `--test-name-pattern`; для
нескольких — `"pie|bar"`):

```bash
node --test --test-name-pattern "pie" \
  tests/pie.test.js tests/small-frames.test.js tests/copy-paste.test.js \
  tests/placement.test.js tests/layer-parsing.test.js
```

Когда менялся общий код или хелперы — обязательно добавить:

```bash
node --test tests/harness.test.js tests/helpers-unit.test.js
```

В `helpers-unit.test.js` есть проверки «all copies of X behave identically»:
они ловят расхождение пяти копий одной и той же функции между плагинами.

Запуск директорией (`node --test tests/`) в Node 25 не работает — только glob
или перечисление файлов.

## Шаг 3. Разобрать результат

Итоговые строки: `ℹ tests / pass / fail / todo`.

- **fail 0** → зелено. Сказать, сколько тестов прошло и сколько `todo`.
- **todo N** → это **не** падения: так помечены задокументированные баги
  (правильное поведение уже описано тестом, он станет проходить после починки).
  Их список и диагноз — в разделе «Известные баги» в `tests/README.md`.
  Не выдавать их за новые проблемы и не «чинить» тест ради зелени.
- **fail > 0** → разобрать каждое падение: имя теста, сообщение ассерта,
  `file:line`. Для каждого решить и сказать явно, что это:
  1. **реальный баг в плагине** — показать причину в `code.js` (строку),
     предложить починку, но не менять код плагина без запроса;
  2. **устаревшее ожидание теста** — поведение изменили сознательно, тест надо
     обновить;
  3. **артефакт мока** — типичные две ловушки описаны в `tests/README.md`:
     значения из VM-realm (`assert.deepEqual` падает на прототипе → оборачивать
     в `plain()`) и приближённые метрики текста (нельзя ассертить абсолютные
     ширины). Артефакт правится в `tests/helpers/`, а не в плагине.

Никогда не помечать падение `todo`, не убедившись, что это реальный баг
плагина, и не описав его причину.

## Шаг 4. Показать общую сводку

По завершении прогона **всегда** выводить пользователю итоговую сводку — даже
если всё зелёное и падений нет. Без неё ответ считается неполным.

Сводка включает:

1. **Вердикт одной строкой** — прошло / есть падения, и что это значит для
   правки, которую проверяли.
2. **Числа**: сколько тестов запущено, `pass`, `fail`, `todo`, время прогона.
3. **Что именно прогнано** — какие типы чартов и файлы тестов, и напоминание,
   что каждая сьюта покрывает и отдельный плагин, и вкладку сводного
   генератора. Если прогнаны не все типы — прямо сказать, что осталось
   непроверенным.
4. **Таблицу по сьютам**, когда файлов было больше одного:

   | Сьюта | Тестов | Прошло | Падений | Todo |
   | --- | --- | --- | --- | --- |
   | `pie.test.js` | 74 | 74 | 0 | 0 |

5. **Падения** — по каждому: имя теста, `file:line`, причина и квалификация
   (реальный баг плагина / устаревшее ожидание теста / артефакт мока).
6. **Известные баги (`todo`)** — коротким списком, по одной строке на баг, с
   пометкой, что это ожидаемо и уже задокументировано в `tests/README.md`.
   Если какой-то `todo` внезапно стал проходить — сказать об этом отдельно: баг
   починен, маркер надо снять.
7. **Что дальше** — конкретный следующий шаг: что починить, какие типы
   допрогнать, нужна ли ручная проверка в Figma.

Сводку давать текстом в ответе, а не отсылкой к логу прогона: пользователь
вывод `node --test` не видит.

## Шаг 5. Что дальше

- Если правка влияла на внешний вид или на окно плагина — напомнить, что
  отрисовку, iframe UI, буфер обмена и шрифты автотесты не проверяют:
  чек-лист ручной проверки в Figma — [tests/MANUAL_QA.md](../../../tests/MANUAL_QA.md).
- Если добавлена новая опция чарта — её тест место в сьюте своего типа; новый
  размер фрейма или набор опций добавляется в `tests/helpers/fixtures.js`
  (`SIZES`) или в `COMBOS` в `tests/small-frames.test.js` и дальше попадает в
  матрицу автоматически.
- Если менялся общий код и прогнаны не все типы — сказать об этом прямо и
  предложить полный прогон.

## Чего не делать

- Не запускать тесты «на всякий случай» по всему репозиторию, если пользователь
  попросил один плагин, — но и не молчать о том, что общий код тянет за собой
  остальные типы.
- Не ослаблять ассерты и не удалять тесты, чтобы прогон стал зелёным.
- Не коммитить результат без явной просьбы.
